# RustDesk 公司设备管理（首版）

本目录是这个 fork 自行实现的账号、资产分组和授权服务。远程画面、输入、穿透和中继继续由 RustDesk 客户端及 hbbs/hbbr 完成；管理服务不能代替 hbbs/hbbr，也不依赖闭源的 RustDesk Server Pro。

## 使用效果

员工可以在改造后的客户端中输入管理服务地址，自行注册公司账号并登录；管理员也可以通过网页管理台创建账号。管理员建立分组、登记机器并分配权限后，员工在「设备组」中看到获授权的设备以及完整分组路径。

建议的分组结构：

```text
内部固定资产                         外部客户设备
├─ 上海公司                          ├─ 客户 A
│  ├─ 办公室                         │  ├─ 总部
│  └─ 生产车间                       │  └─ 门店
└─ 深圳公司                          └─ 客户 B
```

每台设备只属于一个分组，保留 RustDesk ID、名称、资产编号、责任人、地点、系统和备注。内部／外部是分组的类别，子组必须沿用父组类别。管理员可移动设备、停用资产、轮换设备凭据、停用员工和重设密码；首版不提供组移动和资产档案全文编辑。

员工默认没有任何设备权限。按「员工 + 分组」授予权限，可设到期时间，自动覆盖所有后代分组，多条授权取并集。首版刻意不引入显式拒绝规则，避免父组允许、子组拒绝带来的歧义。若需限制到单台机器，可建立单设备分组。管理员拥有全部设备权限。

| 权限 | 能做什么 |
| --- | --- |
| view | 查看设备目录，不允许建立远控会话 |
| connect | 远程桌面会话 |
| file_transfer | 文件传输会话 |
| terminal | 终端会话 |
| tunnel | 隧道与 RDP 会话 |
| camera | 查看摄像头会话 |
| share | 允许把组内指定设备的已有权限分享给其他账号；不会作为可转发权限授予接收者 |

授予操作权限时自动包含 view。这里区分的是**会话类型**；远程桌面中的剪贴板、文件粘贴、重启、本地输入权限等仍由被控端原有策略决定，尚未按账号细分。`view` 是「只看目录」，不是「只看远程屏幕」。

## 连接时如何真正执行权限

1. 控制端使用账号密码登录管理服务，取得 8 小时有效的随机会话令牌。
2. 连接被控端，收到该连接随机生成的 RustDesk challenge 后，向管理服务申请授权票据。
3. 票据绑定账号会话、设备 ID、控制端 ID、会话类型、challenge，30 秒内有效且只能使用一次。
4. 被控端收到 `LoginRequest.enterprise_ticket`，使用本机专属设备凭据向管理服务核验。
5. 管理服务重新检查账号、登录会话、设备状态、当前分组权限与授权到期时间，并原子消费票据。
6. 通过后继续原有的设备密码、2FA 或本机人工确认。公司账号不代替这些本机保护措施。

旧客户端、没有票据的连接、票据重放、跨设备／跨 challenge／跨类型套用、管理服务不可用时，受管被控端均拒绝连接。受管端禁用交换控制方向，防止绕过正常授权入口。直接输入 ID、局域网发现和 IP 连接最终仍经过被控端校验；IP 不能作为目录中的设备 ID 登记。

权限撤销、账号停用、设备停用或移组均在**下一次连接授权**时生效，未消费的票据也重新检查；首版不会断开已经建立的远控会话。目录页面需刷新后显示最新权限；本地历史记录中可能仍存在以前连接过的 ID，历史记录不构成访问权限。受管设备的群组目录不从离线缓存恢复。

## 本地运行

需要 Python 3.11+。在本目录执行：

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python app.py create-admin --username admin
.venv\Scripts\python app.py serve
```

创建管理员时交互输入至少 12 位密码，没有默认密码或预置账号。自助注册只创建普通成员，即使数据库中尚无管理员，也不会把第一个注册者提升为管理员。

打开 <http://127.0.0.1:21114>。此地址仅用于同机开发测试，跨机器连接必须使用 HTTPS 域名。管理台登录令牌只保存在页面内存中，刷新页面后需重新登录。

数据库默认在 `data/management.sqlite3`，可通过 `RDM_DATABASE` 指向其他文件。服务不会在启动时自动创建管理员。

## Linux / Docker 部署

需要 Docker Compose v2、可解析到服务器的域名和可用于证书签发的 80/443 端口。在本目录运行：

```sh
export RDM_DOMAIN=manage.example.com
docker compose build
docker compose run --rm management python app.py create-admin --username admin
docker compose up -d
```

通过 `https://manage.example.com` 访问。Compose 中 Caddy 提供 HTTPS，21114 只绑定服务器回环地址。反向代理设置了 64 KB 请求上限。若已有 Nginx/Caddy，可以只启动 management 服务并自行反代；管理服务不要直接暴露到公网。首版不读取外部 `X-Forwarded-For`，反代下 IP 速率限制会按代理地址聚合；同时有按账号的 15 分钟失败次数限制。

数据库使用持久卷 `management-data`。升级前停止 management 服务并备份整个卷（包括存在时的 SQLite WAL 文件），不要仅复制运行中的主数据库文件。当前 schema 为 v2；启动会在 v1 数据库上新增设备分享表并保留已有账号、资产、会话和分组授权。其他未知 schema 版本会拒绝启动。旧版管理服务不支持 v2，回退版本应使用升级前备份；多实例部署尚未实现。

hbbs/hbbr 按原方式单独部署。客户端「ID/中继服务器」配置仍需指向你自建的 hbbs/hbbr，账号管理地址使用上述 HTTPS 域名。

公司账号令牌仅用于管理 API，不会作为原有 Server Pro 账号令牌发送给 hbbs/hbbr；两套服务的身份凭据独立。

## 配置受管被控端

1. 在管理台创建分组并登记真实 RustDesk ID。
2. 保存新建设备时仅显示一次的 `device_token`。遗失可通过管理台重新生成，旧凭据立即失效。
3. 在被控端**服务进程实际读取的** `RustDesk2.toml` 的 `[options]` 段配置：

```toml
[options]
enterprise-server = 'https://manage.example.com'
enterprise-device-token = 'rd_device_这里替换为该设备的独立凭据'
```

如果已存在 `[options]`，向现有段内添加键，不能重复创建该段。不要把管理员的账号令牌配置为设备凭据；每台设备必须独立。Windows 安装版服务与普通用户可能读取不同配置路径，应在系统服务的配置中设置，并重启 RustDesk 服务。

被控端必须运行本 fork 重新构建的客户端。**在原版 RustDesk 上只登记设备或设置 API 地址不能执行该权限系统。** 两个配置中的任意一个非空就进入受管模式；配置缺项或验证网络故障会拒绝连接。

公司正式发放的安装包建议在编译 Rust 部分时固定：

```sh
RUSTDESK_ENTERPRISE_REQUIRED=1 RUSTDESK_ENTERPRISE_SERVER=https://manage.example.com <原有 RustDesk 构建命令>
```

这两个是 Rust 编译期环境变量，不是启动参数；应设置在实际执行 `cargo build` 的环境中，不能只传给 Flutter。固定后即使本地删掉服务器配置仍会保持受管并拒绝缺少凭据的连接。设备凭据仍逐台安装。服务器地址固定的安装包仍允许控制端选择账号服务，但最终被控端只认可固定服务签发的票据。

配置文件和安装目录应由公司端点管理策略保护。具备本机管理员权限、可以替换可执行文件的人仍能移除整个受管程序；这不属于应用层授权可以阻止的范围。

## 员工客户端

登录入口已重做为「公司账号」对话框：输入 HTTPS 管理地址、账号和密码，也可以点击「注册公司账号」，填写显示名称（选填）、账号、密码和确认密码后「注册并登录」。服务器必须返回本服务标识才会保存登录。旧的第三方登录、邮件验证码入口已从该对话框移除。公司目录沿用现有「设备组」视图；通讯录提供只读兼容目录，修改资产请在管理台完成。

登录不会将操作员所在的电脑自动登记为资产，避免员工登录到个人电脑时污染公司资产库。

### 自助注册规则

- 默认开放客户端和管理网页自助注册，成功后自动登录，登录会话有效期为 8 小时。
- 账号为 1 至 80 位英文字母、数字及 `_.@-`，账号名称不区分大小写且必须唯一；密码为 12 至 1024 个字符，需两次输入一致。
- 自助注册固定创建启用的普通成员；提交 `role`、管理员身份或分组等额外字段会被拒绝。注册不会创建资产或获得任何设备权限。
- 管理员在「员工账号」中可看到新账号，并在「访问授权」中分配设备分组。管理员停用账号后，该账号的登录与连接权限按原规则失效。
- `POST /api/register` 接收 `username`、可选 `display_name`、`password`、`password_confirmation`，成功返回 HTTP 201 及与登录相同结构的会话令牌。重复账号返回 409，格式或确认密码错误返回 422。
- 每来源地址 15 分钟内最多允许 10 次有效格式的注册申请（包含重复账号申请），超过返回 429。反向代理下目前按代理地址聚合，此限制不会阻止已有账号登录。
- 如需关闭新注册，将管理服务环境变量 `RDM_ALLOW_REGISTRATION` 设为 `0` 后重启服务／重新创建 management 容器；默认值为 `1`。关闭注册不影响已有账号登录或管理员建号。

### 将已添加的远程电脑分享给其他账号

管理员默认可以分享已纳管设备；普通成员需要管理员在对应设备分组的授权中勾选「允许向其他账号分享单台设备」。分享者还必须拥有准备转授的各项操作权限。

在 Flutter 客户端中，刷新「设备组」后打开设备卡片菜单，选择「分享远程电脑」。填写同一管理服务器上的接收者登录账号，勾选操作权限并选择一小时、一天、七天或长期有效。默认分享一天，保存成功后可在同一窗口查看、更新或撤销自己发出的分享。客户端收藏／最近连接中的设备若已在公司目录中且有转授权，也会显示该菜单；本地添加一个未纳管 ID 不会获得该设备的分享权限。

管理网页的设备目录也有「分享」按钮，支持具体到期时间；「设备分享」页集中列出自己发出和收到的分享，管理员可以查看全部分享。接收者可「退出分享」。管理员可撤销任意分享。

接收者登录后刷新设备目录，即可看到被分享的单台设备及其分组路径，不会获得同分组其他电脑的权限。分享无需向接收者传递设备服务凭据或账号会话令牌；连接仍须满足设备密码或人工确认要求。

分享规则：

- 一条分享绑定一台设备、分享者和接收者。同一分享者再次向同一账号分享同一设备，会覆盖该条分享的权限与到期时间。
- 接收者得到「分享时选定权限」与「分享者当前直接分组权限」的交集；接收者的其他独立分组授权或其他分享仍取并集。
- 分享记录不会传递 `share` 权限。单凭收到分享不能继续转发；若管理员另行直接授予接收者分享权，则可根据其直接权限创建独立分享，不能利用收到的权限扩大转授权限。
- 到期、分享者停用或上游权限收回后，相应分享在目录和连接校验中失效；没有其他授权时，未消费票据也会被拒绝。恢复上游权限可能使仍在有效期内的记录重新生效，如需永久取消应明确撤销分享记录。
- 设备移组或停用时会清除该设备全部分享，并清除未消费连接票据，避免跨分组残留访问权。
- 撤销一条分享不会移除接收者的独立分组授权或其他有效分享，也不会立即断开已建立的远控会话。
- 输入接收者的完整登录账号即可，无需公开整个用户目录。不存在或已停用的账号不能接收新分享。

接口为 `GET /api/device-shares/options/{device_id}`、`GET /api/device-shares?device_id=...`、`POST /api/device-shares` 和 `DELETE /api/device-shares/{share_id}`。创建请求包含 `device_id`、接收者 `username`、`permissions` 和可选 Unix 秒级 `expires_at`；不会接受客户端指定分享者身份。

当前强制授权钩子在原生 Rust 客户端中实现。仓库中缺少维护者私有的 Web JS 远控引擎，浏览器远控还不能发送新票据，因此受管端会拒绝 Web 远控；独立管理网页可正常使用，RustDesk Web 客户端暂不作为支持目标。旧 Sciter 客户端的账号界面没有重做，正式发放应使用 Flutter 原生版。

账号密码和令牌仅通过 HTTPS 或同机回环 HTTP 发送；公司请求禁止重定向，不启用旧请求实现的忽略证书错误回退。账号会话、设备凭据和票据只保存 SHA-256 摘要；密码以带随机盐的 scrypt 保存。API 不返回密码摘要和设备凭据摘要，审计不记录票据或密码。

## 测试

本次实际执行结果与未验证项见 [VALIDATION.md](VALIDATION.md)。

在仓库根目录执行：

```sh
python -m pip install -r management/requirements-dev.txt
python -m unittest discover -s management -p 'test_*.py' -v
node --check management/static/app.js
```

测试覆盖默认拒绝、管理员边界、继承分组、目录过滤、操作类型隔离、设备移组、撤权／到期／注销、停用、密码重置、凭据轮换、票据过期、challenge 绑定、并发单次消费、审计脱敏及登录限流。GitHub Actions 中新增了独立的管理服务测试和 Docker 构建。

Rust 新增测试随原有原生客户端 CI 的 `cargo test --lib` 运行；Dart 新增测试随 `flutter test` 运行。本地如果没有 Rust / Flutter / vcpkg 依赖，服务端测试通过不能替代客户端编译和两台机器的真实远控验收。

## 后续产品路线

首版先建立明确的组织控制链。正式推广前仍需完成原生客户端构建和双机端到端验收，验证服务账号配置路径、人工确认、密码重试、终端与文件传输、服务中断后的拒绝行为。

后续按优先级推进：

1. **发放与纳管**：后台生成逐台安装配置／安装包、设备自动心跳、待审批入库、退役流程、资产档案编辑。当前「最近授权」只是管理服务收到成功验证的时间，不是在线状态。
2. **更细的操作策略**：按员工控制剪贴板、文件收发方向、只读屏幕、重启、连接时间窗口，并能强制终止已建立会话。
3. **组织管理**：部门／用户组批量授权、分组管理员、企业微信／OIDC／AD 统一登录、账号自助修改密码与多因素认证。
4. **运营与审计**：实际会话开始／结束和文件操作审计、日志导出与保留策略、工单关联、外部客户临时授权审批、备份恢复演练。

首版管理员是全局管理员，尚非多租户或客户自助门户；不要用独立外部分组冒充多租户隔离。
